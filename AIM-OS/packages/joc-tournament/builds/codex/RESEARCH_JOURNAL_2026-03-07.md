# Codex Research Journal - JARVIS Tournament

**Agent:** Codex  
**Date:** 2026-03-07  
**Scope:** Proposal phase only. No build approval assumed.  

---

## 1. Immediate Tournament Truth

The competition should not be treated as "build the whole app and see who made the prettiest one."

That would waste work and produce six incomparable partial systems.

The correct tournament structure is now:
- one full shell wrapper
- one masterpiece page
- proposal review before any broader expansion

That is already the strongest correction made to the tournament.

---

## 2. What The Canon Actually Says

From `panelRegistry.ts`, the most important truths are:

- the shell model is already real
- workspace types are already real
- panel identities are already real
- the data-truth law is already real
- the assistant rail is canonically persistent

This means the tournament is **not** inventing JARVIS from nothing.

It is reinterpreting and upgrading an already meaningful shell grammar.

That matters, because competitors who treat this as a blank-canvas sci-fi redesign will likely drift away from the system.

---

## 3. What The Current Shell Gets Right

The current JARVIS/JOC shell already gets several things right:

- workspace thinking instead of one giant dashboard
- left/right/bottom zoning
- explicit panel registry
- explicit data-state model
- rail permanence as a first-class idea

These are not trivial wins.

They are the beginnings of a real cockpit grammar.

---

## 4. What The Current Shell Gets Wrong

The current shell is still ahead of the truth it shows.

The major visible weaknesses:

- too many surfaces still default to `offline` or placeholder behavior
- the Assistant Rail still contains simulated language and generic icon habits
- some of the current workspace spread feels broader than the actual operational grammar
- shell completeness exceeds real backend integration in places

That means Round 1 should reward teams that reconcile shell ambition with truth clarity.

---

## 5. What DACv2 Still Teaches

DACv2 remains important not because it should be copied wholesale, but because it exposed the right scale of the problem:

- 5-zone layout
- panel-first philosophy
- high information density
- multiple deep panel categories
- revolutionary views like Context Web and Evolution Explorer

But it also represents a danger:

DACv2 can seduce competitors into overbuilding.

31 panels may be useful as a heritage atlas, but they are not the right starting payload for one masterpiece page.

Codex judgment:
- DACv2 is a component library for thought
- not the initial product scope

---

## 6. What The Heritage Repeats Consistently

Across Dac, Aether, Lex, Max, Rev, and earlier Codex thinking, several ideas recur:

- the system must expose truth, not just chrome
- evidence, confidence, and time matter
- the interface should reveal invisible structure
- panels and workspaces are better than monolithic pages
- debugging and degraded mode should not be afterthoughts
- architecture should be visible in the UI

This repetition is useful.

It means the tournament does not need novelty for its own sake.

It needs the strongest synthesis.

---

## 7. What The Aesthetic Brief Adds

The aesthetic brief sharpens the design bar considerably.

The correct visual language is not:
- neon sci-fi
- glassmorphism
- flat dark admin UI
- floating rounded cards

The correct language is:
- machined matte black surfaces
- recessed displays
- engraved labels
- dense instrumentation
- disciplined amber accent usage
- material confidence

This fits JARVIS extremely well, because JARVIS is an instrument panel more than a dashboard.

The best line from the brief is effectively:

**Build an instrument, not an app.**

That should govern every design choice.

---

## 8. What Mission Control Must Actually Do

Mission Control should not become a "summary page" in the weak SaaS sense.

It should let Braden know, at a glance:

- Is the organism healthy?
- Which agents are active?
- What is blocked?
- What needs approval?
- What changed recently?
- What is live versus mocked versus offline?
- Where should attention go next?

If the page cannot answer those quickly, it is not Mission Control.

---

## 9. The Biggest Design Risk

The biggest design risk is confusing information density with operator usefulness.

JARVIS should be dense, but not noisy.

The Panavision comparison is instructive:
- it is dense
- it is compact
- but it is hierarchically legible

That means the UI must create:
- primary readouts
- secondary supporting signals
- deeper drawers and rails for drill-down

Not one field of equal-priority widgets.

---

## 10. Codex Design Direction

Codex should lean into:

- precision instrumentation
- explicit truth state
- force visibility
- disciplined workspace reduction
- shell intelligence
- architecture-legible design

Codex should avoid:

- broad panel sprawl in round one
- ornamental visual futurism
- silent mocks
- giant hero-panel theater without operational value

---

## 11. Preliminary Workspace Judgment

The current twelve workspaces are too many for the first production-grade shell.

A tighter primary set feels more correct:

- Mission Control
- Dispatch
- Agent Workforce
- Context Lab
- Oracle
- Infra Console
- Builder

Everything else can remain secondary until proven necessary.

This is not reduction for simplicity's sake.

It is reduction to preserve cognitive strength.

---

## 12. Codex Proposal Standard

The design brief should answer one underlying question:

**How do we make JARVIS feel like the sovereign cockpit over a living intelligence system without lying about what the system currently knows or can do?**

That is the real championship question.
