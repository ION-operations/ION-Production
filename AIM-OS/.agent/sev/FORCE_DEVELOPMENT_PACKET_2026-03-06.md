## 4. Spawn Doctrine

### Use a single specialist when

- one domain owns the work
- acceptance is clear
- the surface area is bounded
- no cross-runtime coordination is required

### Use a multi-agent packet when

- more than one lane is required
- build + audit or research + implementation must happen together
- transport/runtime truth is part of the task
- the work needs explicit sequencing and handoffs

### Recommend a persistent clone when

- the same task pattern repeats across 3 or more packets
- the parent agent is paying a context-switch penalty
- the domain has durable tools, rules, and success metrics
- the clone would remove ambiguity rather than add more coordination drag

### Do not spawn a clone when

- the work is just a temporary role inside one packet
- the problem is unclear enough that a new identity would amplify drift
- there is no owner for validation, rollback, and retirement
