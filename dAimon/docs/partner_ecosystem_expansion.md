# Partner Ecosystem Expansion

dAimon should not present partner support as a pile of integrations. The product
claim is stronger and cleaner:

```text
Every partner becomes a governed context surface.
dAimon decides what future AI work may inherit from it.
```

MongoDB remains the primary contest proof substrate. The other partner lanes
should be represented as expansion surfaces with explicit adapter manifests,
proof obligations, and non-claims until live evidence exists.

## Contest Posture

The contest path stays narrow:

```text
MongoDB + Gemini + Agent Builder + dAimon trust layer
```

That path proves the core governed inheritance loop:

```text
candidate work -> MongoDB continuity state -> accepted-only retrieval -> receipt citations -> Gemini handoff
```

The partner ecosystem roadmap shows that the same law can extend to Arize,
Elastic, Fivetran, and GitLab without claiming those integrations are already
implemented.

## Partner Map

| Partner | dAimon role | Governed surface | Contest posture |
| --- | --- | --- | --- |
| MongoDB | Continuity state and operational memory | Continuity objects, receipts, settlement queue, inheritance bundles, MCP trace | Primary live proof |
| Arize | Observability and evaluation | Model/tool/retrieval traces, eval results, failure annotations | Next-best expansion |
| Elastic | Evidence search and retrieval | Searchable receipts, claims, rejected branches, logs, artifacts | Search expansion |
| Fivetran | Enterprise data ingestion | Source connector syncs, destination freshness, ingestion proof | Enterprise ingestion expansion |
| GitLab | SDLC governance | Issues, merge requests, CI, security scans, approvals, deploy evidence | Developer workflow expansion |

## Adapter Law

Every partner adapter should answer the same questions before any object becomes
inheritable:

```text
What can this partner read?
What can it write?
What authority is required?
What proof can it return?
What freshness and provenance does it expose?
What objects are candidate, accepted, rejected, stale, or secret-bearing?
What should future agents be allowed to inherit?
```

The normalized path is:

```text
partner system
-> adapter manifest
-> capability declaration
-> object normalization
-> authority classification
-> proof requirements
-> settlement policy
-> receipt
-> inheritable context object
```

## Expansion Order

```yaml
partner_expansion_order:
  1_mongodb:
    status: primary_proof_substrate
    goal: state, receipts, inheritance, MCP trace
  2_arize:
    status: next_best_expansion
    goal: trace/eval layer for dAimon runs
  3_elastic:
    status: search_expansion
    goal: cross-receipt evidence discovery and hybrid retrieval
  4_gitlab:
    status: developer_workflow_expansion
    goal: AI work receipts tied to issues, merge requests, CI, security, deploy evidence
  5_fivetran:
    status: enterprise_ingestion_expansion
    goal: bring enterprise sources into governed context lanes
```

## Non-Claims

dAimon should not claim live Arize, Elastic, Fivetran, or GitLab integration
until each adapter has a live trace, receipt, validation artifact, and dashboard
proof. Until then, the correct claim is:

```text
dAimon has a partner adapter architecture and a MongoDB-proven first slice.
```
