# ION Custom GPT v4.7 — Project Context Package Dogfood Contract

## Purpose

v4.7 turns the v4.2–v4.6 architecture into a concrete, self-tested package
system. The carrier must not only describe folder capsules, continuity exports,
dynamic domains, ordered fan-out, and transfer profiles; it must dogfood them by
building context packages from its own folder mesh and proving that a new chat
can remount those packages.

## Product invariant

A state-bearing ION Custom GPT response must be able to produce a portable
context package containing:

1. the relevant folder/domain capsules;
2. the active route and sequence continuation;
3. the visible persona envelope and receipt state;
4. dynamic domain/agent expansions;
5. architecture signals and unresolved design obligations;
6. ordered context fan-out batons and unresolved alerts, when present;
7. transfer profile and omitted-files manifest;
8. a next-chat prompt that instructs the new carrier to mount before answering.

## Dogfood law

The carrier package itself is the first test subject. When v4.7 is run, it must
build an `ion.context_package.v1` object for
`custom_gpt_sandbox_carrier`, package it with the context mesh, and then run a
remount simulation that verifies the active objective, authority boundaries,
candidate domains/agents, profile state, receipts, and next sequence can be
recovered from package files alone.

## No-loss bridge

Any architecture signal captured in chat must appear in at least one durable
object:

- `ion_architecture_signal`;
- route requirement;
- protocol file;
- schema;
- test;
- receipt;
- context package entry;
- continuity export entry.

If the system cannot implement the signal in the current turn, it must export it
as an unresolved design obligation so that a future chat can recover it.
