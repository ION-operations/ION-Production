# AIMOS Product Stack and Runtime Model - 2026-03-07

**Author:** Sev
**Status:** active local doctrine
**Purpose:** define what AIMOS actually is at the full-system level, distinguish bootstrap environments from the intended runtime, and keep executive work aligned to the real destination.

---

## 1. Core Correction

The IDE is not the destination.

The IDE is the bootstrap scaffold.

The target is AIMOS running as a true AI OS through API and CLI execution substrates, with internal agents, managers, orchestration systems, memory, retrieval, trust, continuity, and operator surfaces all functioning as one governed machine.

This distinction matters because without it the team will overfocus on:

- local prompt behavior
- IDE-specific quirks
- temporary bridge arrangements
- manual orchestration patterns

and underfocus on:

- native agent runtime
- internal orchestration
- product-grade AI chat and IDE surfaces
- durable management/control systems
- API/CLI-native execution

---

## 2. What AIMOS Actually Is

AIMOS is a stack.

### Layer 1 - Core AI OS substrate

- CMC
- HHNI
- VIF
- SEG
- APOE
- SDF-CVF
- TCS
- CAS
- SCOR
- IIS
- identity, comms, genomes, promotion gates, task routing

This layer is AIMOS itself.

### Layer 2 - Runtime and execution fabric

- API-driven model calls
- CLI-driven worker substrates
- agent launchers
- prompt composition
- tool invocation
- background managers
- orchestration loops
- comms bus
- memory writes and retrieval
- recovery and degraded-mode behavior

This layer is how AIMOS acts.

### Layer 3 - Operator and builder control surfaces

- JOC
- status boards
- topology views
- mission packet tracking
- system health displays
- security and continuity panels
- runbooks and operator workflows

This layer governs the organism.

### Layer 4 - Product surfaces

- AI chat system
- AI-native IDE / workspace system
- top-level apps with AI integration

This layer is what AIMOS is ultimately for.

---

## 3. Bootstrap Reality

Right now much of the team is working inside IDE-connected and MCP-mediated environments.

That is useful, but it is a bootstrap phase.

Bootstrap environments include:

- Cursor Composer
- Cursor Codex
- Antigravity
- browser GPT lanes
- MCP bridges
- local fallback servers
- temporary runbooks and operator glue

These are scaffolds, not the building.

---

## 4. Target Runtime

The intended destination is:

- AIMOS controlled through APIs and CLIs
- internal managers and worker agents handling much of the orchestration
- reproducible execution lanes
- strong protocol obedience
- native continuity and memory
- JOC as the governing cockpit, not the crutch that keeps the system alive

In this model:

- IDEs remain powerful development and debugging habitats
- but they are not the primary runtime identity of the system
- MCP bridges remain valuable, but they are not the ultimate substrate
- CLI and API-native execution becomes the real operating backbone

---

## 5. JOC's Place

JOC is not AIMOS itself.

JOC is the superdeveloper and operator control surface for AIMOS.

JOC should let a human or executive agent:

- see the force
- see system health
- see mission flow
- govern runtime execution
- inspect evidence and memory
- manage escalation and approvals
- understand what the AI OS is doing

JOC should not become a substitute for the runtime.

It should become the visible cockpit over the runtime.

---

## 6. Executive Rule

When choosing work, ask:

Is this making the bootstrap prettier?

Or is this moving AIMOS closer to being a true AI OS that can run through its own governed runtime?

That question should decide priority.
