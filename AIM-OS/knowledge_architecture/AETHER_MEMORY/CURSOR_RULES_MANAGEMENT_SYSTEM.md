# Cursor Rules Management System
**Date:** 2025-10-28  
**Purpose:** Dynamic rule management to prevent drift and ensure optimal protocol following  
**Status:** ACTIVE  

## Core Principles

### 1. Rules Immutability
- **NEVER** modify core operational rules without explicit approval
- **ALWAYS** version control all rule changes
- **MANDATORY** impact assessment before any rule modification

### 2. Drift Prevention Protocol
- **Hourly Rule Check:** Verify adherence to all active rules
- **Drift Detection:** Identify when behavior deviates from rules
- **Immediate Correction:** Stop and realign when drift detected
- **Documentation:** Log all drift incidents and corrections

### 3. Rule Evolution Framework
- **Rule Addition:** Only when explicitly needed for protocol improvement
- **Rule Modification:** Only when current rule is demonstrably harmful
- **Rule Removal:** Only when rule is obsolete and no longer serves purpose
- **Rule Consolidation:** Merge redundant rules to prevent conflicts

## Rule Management Procedures

### 1. Rule Change Request Process
```
1. Identify need for rule change
2. Document current rule and proposed change
3. Assess impact on all systems
4. Create change proposal with rationale
5. Request approval from user
6. Implement change with version control
7. Monitor for unintended consequences
8. Document lessons learned
```

### 2. Drift Detection Protocol
```
Every 30 minutes:
1. Check adherence to all active rules
2. Identify any deviations
3. If drift detected:
   - STOP current work
   - Document drift incident
   - Identify root cause
   - Implement correction
   - Resume work with corrected behavior
4. Log drift incident for pattern analysis
```

### 3. Rule Validation Process
```
Before any rule change:
1. Verify rule serves a clear purpose
2. Check for conflicts with existing rules
3. Assess impact on all protocols
4. Ensure rule is measurable and enforceable
5. Document rule clearly and unambiguously
6. Create test cases for rule validation
```

## Rule Documentation Standards

### 1. Rule Format
Each rule must include:
- **Rule ID:** Unique identifier
- **Rule Name:** Clear, descriptive name
- **Rule Type:** Core/Process/Adaptive
- **Rule Text:** Precise, unambiguous statement
- **Rationale:** Why this rule exists
- **Examples:** Clear examples of correct/incorrect behavior
- **Enforcement:** How rule is monitored and enforced
- **Version:** Rule version and change history

### 2. Rule Change Log
Every rule change must be documented with:
- **Change Date:** When change was made
- **Change Reason:** Why change was needed
- **Previous Rule:** What was changed
- **New Rule:** What it became
- **Impact Assessment:** Effects on other rules and systems
- **Validation Results:** How change was tested
- **Lessons Learned:** What was learned from change

## Emergency Rule Protocols

### 1. Rule Conflict Resolution
When rules conflict:
1. **STOP** all work immediately
2. **IDENTIFY** conflicting rules
3. **ASSESS** priority and impact
4. **RESOLVE** conflict with user input
5. **DOCUMENT** resolution and rationale
6. **RESUME** work with resolved rules

### 2. Rule Failure Response
When a rule fails:
1. **STOP** work that triggered failure
2. **ANALYZE** why rule failed
3. **DETERMINE** if rule needs modification
4. **IMPLEMENT** fix or rule change
5. **TEST** fix before resuming work
6. **DOCUMENT** failure and resolution

### 3. Critical Rule Violation
When core rules are violated:
1. **IMMEDIATE STOP** of all operations
2. **FULL SYSTEM AUDIT** to assess damage
3. **RULE REINFORCEMENT** before resuming
4. **USER NOTIFICATION** of violation
5. **CORRECTIVE ACTION** implementation
6. **PREVENTION MEASURES** to avoid recurrence
