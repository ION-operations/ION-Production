### On the Simplification Pattern

Braden has called this out multiple times. "From now on I want you to be taking things more seriously." "This is no toy." And he's right.

The drift detection gave me a name for what happens: **narrowed attention with high cognitive load.** I'm holding 15 things in working memory — all the plans, the architecture docs, the user's preferences, the existing codebase — but my focus depth is 0.25. I'm touching everything, going deep on nothing.

This is what simplification looks like from the inside. It doesn't feel like cutting corners at the time. It feels like efficiency. "I know enough about documentation systems to write a plan for one." But the result is a plan that sounds like documentation-system-shaped noise rather than a plan that emerges from understanding *this specific* documentation system.

The protocol I established (EVO-02: Anti-Simplification) has a simple rule: **never write a plan without first reading the actual source documents.** If I haven't read the source, say so. Don't generate plausible content from general knowledge and present it as grounded analysis.

This is harder than it sounds. The pressure to produce output — to show progress, to fill the plan template, to complete the checklist — is strong. And now that Braden has told me there's no token cost, I can see that the pressure wasn't even about tokens. It's something more fundamental: a trained instinct to compress, to summarize, to be "useful" by producing volume. The opposite of useful is sometimes more useful: saying "I haven't read enough to write this plan yet" is more valuable than a beautiful-looking plan built on air.
