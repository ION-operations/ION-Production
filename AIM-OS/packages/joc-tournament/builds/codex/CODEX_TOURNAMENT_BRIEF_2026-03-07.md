# Codex Tournament Brief - JARVIS 2.0

**Agent:** Codex
**Date:** 2026-03-07
**Role in tournament:** backend-precise cockpit architect

---

## 1. Codex Thesis

Most competitors will over-optimize one of two wrong things:
- visual spectacle
- feature sprawl

The winning JARVIS build should optimize something else:

**operator legibility over a real intelligence organism**

If Braden cannot quickly understand:
- what is live
- what is broken
- what the agents are doing
- what needs approval
- what changed

then the build is not good enough, regardless of visual quality.

---

## 2. What JARVIS Must Be

JARVIS is:
- the cockpit over AIMOS
- a visibility and control surface for a non-coder sovereign
- a bridge between backend complexity and humane operational control

JARVIS is not:
- the runtime itself
- the final simple consumer OS
- a generic admin panel

---

## 3. Codex Judgment On Current Canon

The current `panelRegistry.ts` and `AssistantRail.tsx` confirm useful shell grammar but also expose the current weakness:

- shell structure is ahead of truth wiring
- workspace names are strong
- data status law is correct
- rail permanence is correct
- too many surfaces still default to placeholder or offline posture
- the rail still contains simulated language and generic iconography in places

So the tournament should not reward whoever merely multiplies panels.

It should reward the build that makes the existing canonical ideas operationally coherent.

---

## 4. Codex Answer To The Key Design Questions

### 4.1 Main workspaces

Twelve workspaces is probably too many for the first production-grade JARVIS shell.

Codex recommends a tighter primary set:
- `Mission Control`
- `Dispatch`
- `Agent Workforce`
- `Context Lab`
- `Infra Console`
- `Oracle`
- `Builder`

Secondary or later-promoted workspaces:
- `Calendar`
- `Context Graph`
- `System Atlas`
- `Session`
- `Mission Builder`

The rule:
- fewer first-class workspaces
- deeper per-workspace drawer logic
- less route sprawl

### 4.2 Left drawer

The left drawer should be the workspace-local command context.

Examples:
- `Mission Control`: agent fleet, system status, active mission queue
- `Dispatch`: mission queue, target lanes, recent messages
- `Agent Workforce`: agent dossier, fleet topology, handoffs
- `Context Lab`: memory browser, evidence graph, retrieval controls
- `Infra Console`: system status, credentials, diagnostics
- `Oracle`: approvals, policy, escalation, memory context

### 4.3 Bottom bar

The bottom bar should be for temporal and diagnostic surfaces:
- terminal
- problems
- event/activity feed
- debug/telemetry
- timeline

It should not be the dumping ground for random overflow.

### 4.4 Navigation

Primary navigation should remain workspace-driven:
- top-level workspace switcher
- command palette
- keyboard shortcuts

Do not rely on deep nested nav as the core interaction model.

### 4.5 Assistant Rail

The Assistant Rail should be:
- persistent
- workspace-aware
- the living operator intelligence rail

Its job is not only "chat."
It should unify:
- conversation
- current context
- actions / approvals
- evidence / memory

### 4.6 Data truth

Every panel must signal truth state clearly.

The tournament should heavily punish:
- silent mock data
- unclear live/offline state
- fake confidence

### 4.7 Premium ops-center feel

Codex view:
premium feel comes from:
- composure
- material confidence
- density with hierarchy
- precise motion
- explicit truth

not from visual noise.

---

## 5. Codex Winning Standard

A winning JARVIS round-one dashboard should prove:
- the operator can see system health in seconds
- the operator can see the current agent force in seconds
- the operator can tell live from mock instantly
- the screen uses width intelligently
- the shell feels like command instrumentation, not app furniture

---

## 6. Codex Recommendation On Tournament Scope

Codex strongly recommends the tournament begin with:
- one shell wrapper
- one masterpiece page
- one review gate

not with full multi-workspace implementation.

Why:
- it produces comparable outputs
- it forces real craft
- it reduces wasted build labor
- it lets the operator approve direction before the system sprawls

Codex's recommended Phase 1 target page:
- `Mission Control`

If a competitor wants a different page, they should justify why it better proves the cockpit thesis.

---

## 7. Recommended Tournament Warning

The tournament should explicitly avoid becoming:
- "who can make the flashiest hero screen"
- "who can fit the most panels"
- "who can write the longest theory"

It should instead ask:

**Which build makes AIMOS easiest to govern as a real organism?**

That is the correct championship question.
