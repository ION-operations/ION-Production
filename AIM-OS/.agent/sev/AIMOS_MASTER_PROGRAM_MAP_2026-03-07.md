# AIMOS Master Program Map - 2026-03-07

**Author:** Sev
**Status:** active local doctrine
**Purpose:** hold the full-picture definition of AIMOS as an AI OS program, map the major layers, and clarify what the team is actually trying to build.

---

## 1. Program Thesis

AIMOS is not just an MCP server, not just a set of IDE automations, and not just a control dashboard.

AIMOS is an AI operating system program.

Its target form is:
- a governed AI OS substrate
- a runtime fabric of API and CLI workers, managers, memory, retrieval, trust, and orchestration
- a cockpit that lets humans and executive agents inspect and command the organism
- product surfaces such as AI chat, AI-native IDE workflows, and AI-powered applications

The current IDE-connected and MCP-mediated habitats are important, but they are bootstrap environments, not the final identity of the system.

---

## 2. The Five-Layer AIMOS Model

### Layer A - Core AI OS substrate

These are the major systems that define AIMOS as more than a prompt wrapper:

- `CMC` - memory substrate
- `HHNI` - retrieval and long-context navigation
- `VIF` - provenance, confidence, abstention, replay
- `SEG` - evidence graph
- `APOE` - orchestration and execution planning
- `SDF-CVF` - change parity and evolution discipline
- `TCS` - timeline and continuity
- `CAS` - meta-cognitive monitoring
- `SCOR` - sanity and manipulation resistance
- `IIS` - intuition and pattern reasoning

These systems are the organism's internal organs.

### Layer B - Runtime and execution fabric

This is how AIMOS acts:

- MCP control plane
- memory reads and writes
- retrieval calls
- tool invocation
- launcher systems
- API and CLI workers
- background managers
- orchestration loops
- degraded-mode handling
- bus messaging and identity-aware coordination

This layer is the path from intelligence to execution.

### Layer C - Cockpit and operator surface

This is how the force is governed:

- JOC
- status surfaces
- mission packet visibility
- health panels
- security and continuity displays
- audit views
- runbooks and operational control artifacts

JOC belongs here. It is the cockpit, not the engine block.

### Layer D - Product surfaces

These are the user-facing outputs AIMOS is ultimately meant to power:

- AI chat system
- AI-native IDE and workspace
- DACv2 and related IDE-OS builds
- application surfaces that consume the AIMOS runtime cleanly

This is where the program becomes a real product ecosystem.

### Layer E - Bootstrap habitats

These are necessary for current development but should not be confused with the target runtime:

- Cursor Composer
- Cursor Codex
- Antigravity
- browser ChatGPT
- Gemini CLI during early worker experiments
- Codex CLI during bootstrap and hardening
- MCP HTTP bridges and temporary transport shims

These environments help build AIMOS. They are not AIMOS itself.

## 3. Current Reality By Layer

### Core substrate

Repo evidence says the major systems exist in substantial form. `docs/AIMOS_MAJOR_SYSTEMS.md` and `knowledge_architecture/SAM/sources/00_MASTER_AIMOS_SYSTEM_MAP.md` confirm a serious core map, not a fantasy.

Current executive judgment:
- `CMC`, `VIF`, `SEG`, `APOE`, `SDF-CVF`, and much of the MCP plane are strongly real
- `HHNI` remains especially important but operationally suspect and in need of renewed truth-freezing
- `TCS`, `CAS`, `SCOR`, and `IIS` are present but uneven in implementation maturity and runtime trust

### Runtime fabric

This layer is partially real and strategically under-converged.

Current executive judgment:
- AIMOS MCP is real
- live bus messaging is real when transport is healthy
- Codex CLI now has a repo-first launcher path through Forge
- Gemini CLI has prior swarm and minified-server precedent through Opus
- transport remains asymmetric across hosts
- API and CLI worker substrate still needs stronger unification and first-class doctrine

### Cockpit

JOC is real but not yet complete as a governing cockpit.

Current executive judgment:
- shell and UI infrastructure are real
- `AssistantRail` and `panelRegistry` count as real force-surface groundwork
- many pages remain partial
- force visibility and system health need to outrank pure visual polish

### Product surfaces

Product intent is real, but product convergence remains behind core experimentation.

Current executive judgment:
- the AI chat and IDE product direction is clear
- the runtime beneath those products is not yet converged enough to claim production readiness
- product work must now stay tied to runtime and cockpit truth, not drift into disconnected front-end dreams

### Bootstrap habitats

This layer is active and heavily used.

Current executive judgment:
- essential for now
- dangerous when mistaken for the product
- still necessary for the build phase

## 4. What The Program Needs Next

### Program Need 1 - Truth convergence

We need a current source-of-truth collapse across docs, runtime claims, and active systems.

Why:
- too many old answers still exist
- too many local wins are not frozen into one command picture

### Program Need 2 - Runtime backbone

CLI and API worker execution must become a disciplined substrate instead of a series of one-off experiments.

Why:
- that is closer to the intended AI OS runtime than manual IDE prompting
- it allows repeatability, scaling, and bounded workforce operation

### Program Need 3 - Cockpit maturity

JOC must evolve from shell plus partial panels into a true force-governance surface.

Why:
- the operator needs visible truth
- the workforce needs inspectability
- AIMOS cannot be governed at scale through scattered folders alone

### Program Need 4 - Retrieval and continuity integrity

HHNI and related context infrastructure need renewed truth freezing.

Why:
- without strong retrieval, the OS loses intelligence density
- without continuity discipline, the force keeps rediscovering itself

### Program Need 5 - Product path discipline

AI chat, AI IDE, DACv2, and application surfaces must stay anchored to the shared AIMOS runtime.

Why:
- otherwise the project splinters into disconnected app visions

- talking about bootstrap wins as if they are full runtime wins
- treating JOC as the whole system
- treating MCP transport behavior in one host as global truth

## 7. Program-Level Success Criteria

AIMOS is moving correctly when:

- the core systems are easier to reason about together
- runtime execution is becoming reproducible through CLI and API lanes
- JOC is becoming a real cockpit over live systems
- product surfaces are converging on the shared runtime
- the workforce is more visible, measurable, and governable
- the operator no longer has to hold the whole program alone

## 8. Bottom Line

The full picture is this:

AIMOS is an AI OS program with a real systems core, a still-forming runtime backbone, an unfinished cockpit, and ambitious product surfaces.

The IDE is the bootstrap.

The runtime is the goal.

The cockpit must govern the runtime.

The workforce must build toward that destination, not orbit local scaffolding forever.
