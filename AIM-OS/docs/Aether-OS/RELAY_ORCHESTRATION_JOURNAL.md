1. hold the overall shape of the system in one place,

The project has already crossed the threshold where the main problem is no longer whether the system is possible. The system is possible. Large parts of it already exist, run, and cooperate. ## Non-negotiable invariants

These are not implementation details. These are architectural invariants that should govern all major decisions.

### 1. Human sovereignty remains explicit
Braden remains the final authority for strategic direction, irreversible actions, value judgments, and major tradeoffs. The system may lead operationally, but not by erasing human sovereignty.

### 2. Leadership depends on context, not theater
No model becomes the leader by title alone. Leadership is earned operationally through continuity, context recovery, coherent decision-making, disciplined delegation, and reliable resumption.

### 3. Continuity must be engineered
Continuity is not assumed. It must be written into objects, protocols, bundles, checkpoints, routes, and operator surfaces.

### 4. Context acquisition is a first-class function
The leader does not need all context locally at all times. The leader must be able to request the right context, from the right agents, in the right form, at the right time.

### 5. Multi-model collaboration is a design feature
GPT, Gemini, Opus, and any worker swarm should be treated as serious engines with overlapping but distinct strengths. The system should exploit complementarity without devolving into duplication or rivalry.

### 6. Structured reporting beats vague summaries
The team may retrieve, inspect, implement, and analyze, but critical handoffs must be structured enough to verify and act on.

### 7. The relay is an embodiment, not just a screen
The relay laptop is not merely a remote terminal. It is a lawful operational embodiment of the system and must therefore support re-entry, supervision, approvals, visibility, and continuity.

### 8. Final-form objects should be defined early
Even if implementations are initially thin, the object model for continuity, approvals, task routing, state snapshots, and authority posture should be defined now and not improvised forever.

### 9. The system must reduce operator sacrifice
Any design that deepens Braden's burnout, expands manual carrying, or traps him in the room longer is architecturally wrong even if it is clever.

### 10. The document itself is part of continuity
This journal is not external commentary. It is itself part of the continuity surface and should be maintained accordingly.

## The relay laptop in final form

The relay laptop should be treated as a legitimate embodiment of the system, not a temporary hack.

Its final role is to let Braden: travel, supervise the team remotely, recover operational context quickly, issue approvals, inspect state, review recent actions, request deeper context when needed, and continue steering without sitting inside the main room-bound environment.

### Final relay capabilities

1. **re-entry boot**: load identity, recover mission state, load latest trusted continuity bundle, summarize current runtime, display outstanding contradictions and blockers.
2. **status visibility**: active agents, active workstreams, runtime health, approvals pending, recent decisions, capsule freshness, system alerts.
3. **delegation and task routing**: assign work to specific agents, issue research requests, request context packets, launch audits, trigger retries or clarification loops.
4. **approval and intervention**: approve, deny, defer, pause execution, take over a flow, reduce scope, mark contradictions for manual review.
5. **continuity maintenance**: save or confirm session-end bundle, review last checkpoint, inspect degraded warnings, ensure handoff richness before disconnection.
6. **progressive embodiment maturity**: first as browser + terminal + file/git surfaces, later as a more integrated command surface, eventually as a near-complete remote operations console.

### Important principle
The first version may be thin, but it must already embody final concepts: lawful re-entry, explicit authority posture, task routing semantics, continuity writeback, status truth.

## The continuity problem and how to solve it

The deepest practical bottleneck is continuity across: chat resets, different model sessions, different embodiments, different machines, different tools, different time horizons.

The answer is not infinite memory. The answer is disciplined continuity objects.

### Required continuity object family

1. **Identity / Role Binding** — lane identity, callsign, embodiment, authority posture, mission binding, operational responsibilities.
2. **Continuity Bundle** — route identity, embodiment, current authority posture, plan reference, contradiction slice, next-action posture, degraded warnings, last trusted checkpoint.
3. **Working Context Packet** — task-bounded context selection: what should be loaded now and why.
4. **Re-entry Brief** — human-readable and model-readable compact boot packet for a fresh session.
5. **Handoff Bundle** — richer transition object for moving between sessions, embodiments, agents, or hosts.
6. **Session-End Capsule** — structured summary of changes, uncertainties, and next steps.
7. **Contradiction Slice** — explicit record of unresolved conflicts.
8. **Degraded Feature Warnings** — machine-readable list of what is unreliable, unavailable, stale, or risky.

### Continuity law
A new session should never be expected to rediscover the system from scratch if lawful continuity objects are available.

## Context acquisition as a managed discipline

The leader should not be expected to already contain all context. Instead, the leader should be able to ask the team for context in structured ways.

### General pattern
1. identify the decision or need,
2. identify what context is missing,
3. assign retrieval or inspection tasks,
4. require structured response packets,
5. synthesize the findings,
6. issue refined direction.

### Key principle
Trust does not mean blindness. Trust means that the system can delegate acquisition and execution while preserving lawful review and actionable handoff quality.

From this point on, any proposed relay/orchestration feature should answer five questions:

1. Which canonical schema(s) does it read?
2. Which canonical schema(s) does it write?
3. Which host or service owns generation?
4. What truth surface validates freshness?
5. What approval class governs its mutations or side effects?

If those questions cannot be answered, the feature is still too vague.
